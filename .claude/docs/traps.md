# Trap / Gotcha Registry — Trader repo

The canonical, cross-cutting list of traps, gotchas, and process rules for this codebase.
Every skill's GUARDS/gotcha section should embed the 2-6 traps that bite ITS workflow and
link back here for the rest. This file is the **promotion target** for the auto-memory
traps in `~/.claude/projects/.../memory/` — new traps discovered anywhere should land here,
not just in a memory file only one session will ever read.

**Format:** `**Name** — Symptom -> Root cause -> Rule/fix -> Evidence pointer.`

Point-in-time claims (constants, versions, line numbers, file states) are stamped
**"as of 2026-07"**. Numbers drift; the *shape* of the trap does not — verify current
values with the cited lookup before trusting a specific figure.

## 0. The one that inverts everything if you get it wrong

**Scoring direction is CALL-high / PUT-low — never mean-reversion** — Symptom: a doc, memory file, or generated summary describes the system as "overbought at ≥75 / oversold at ≤25", implying a contrarian/mean-reversion style. Cause: an old memory file (`project_overview.md`, ~2026-04 vintage) predates the system's directional-momentum framing, and its overbought/oversold language survives in auto-memory even though it inverts the live invariant. **Rule: HIGH score (≥75) = bullish = BUY A CALL. LOW score (≤25) = bearish = BUY A PUT.** Momentum/trend-following, not reversion-to-mean — the Apex/Core sleeve "buys weakness" only in the sense that DOWN_hard regimes are where the *existing bullish signal* has its best edge (see "Regime concentration of the call edge" below), not because high scores mean "due for a pullback." Assessment buckets (≥70 HIGH-bucket-wins/≤30 LOW-bucket-wins) are a superset of the tighter ≥75/≤25 call/put thresholds — don't conflate them, never invert either. Evidence: CLAUDE.md "CRITICAL — scoring direction" (top of file); auto-memory FLAGS in `memory.md`: "project_overview.md ... frames the system as MEAN-REVERSION with '>=75=overbought, <=25=oversold' — this contradicts the current CRITICAL invariant... Do not promote its framing."

## 1. Infrastructure / DB

**MySQL zombie-query cascade (2013 read-timeout loop)** — Symptom: repeating `2013` errors on queries normally sub-second and indexed. Cause: `database/trader_database.py` sets client-side `read_timeout=30`; pymysql disconnects the CLIENT only — the query keeps running server-side, and each blind retry stacks another zombie until disk IO saturates. Historical trigger: a 10y recalc bulk-insert (1.76M rows) drifted InnoDB stats and knocked a `historic_peaks` JOIN+OR query off its index. Fix: `SHOW FULL PROCESSLIST` first, `KILL <id>` every stacked copy before retesting — never blind-retry. A query taking >30s is a missing index or bad plan, fix with `EXPLAIN` + query restructure, never by raising `read_timeout`. On `scores`, avoid JOIN+OR+ORDER BY in one statement — split the OR into AND-ranges mapping 1:1 onto an index and stitch/sort in Python. See also `debug-pipeline` skill. Evidence: `feedback_mysql_zombie_queries.md`.

**Worktree PYTHONPATH trap (false NULLs)** — Symptom: an experiment run from an `algo-exp/*` worktree silently imports the MAIN checkout's modules instead of the worktree's candidate code; an A/B that should show diffs shows zero (false NULL). Cause: this box's User+Machine `PYTHONPATH` includes `C:\Development\Trader` (and `database` subdir) ahead of `sys.path[0]` (which Python sets to the script's directory, not cwd) — so `python experiments/<x>/<y>.py` run from a worktree still resolves `import database.utils.scoring` etc. to the main checkout. Fix: at the top of every experiment script, `while ROOT in sys.path: sys.path.remove(ROOT)` then `sys.path.insert(0, ROOT)` using the worktree's OWN root, and assert `os.path.abspath(module.__file__).lower().startswith(ROOT.lower())` for at least one imported module — a 0-diff A/B without that origin assert is suspect, not clean. Safe invocations: `python trader.py ...`, or `python -m`/`python -c` with cwd pinned at the worktree root. Evidence: `feedback_worktree_pythonpath_trap.md`; recurs in `research` skill LIVING GOTCHAS (also covers `--cwd` backslash-eating in Git-Bash — use forward slashes — and worktrees having their own EMPTY `task_queue.db`, so always `trader queue submit` from MAIN and point `--cwd` at the worktree).

**Queue stdout buffering hides a running job as a hang** — Symptom: a `trader queue submit` python job's `run.log` stays empty or updates in large stale chunks, indistinguishable from a livelock. Cause: the task-queue launcher gives children cp1252 piped stdout; modules with the defensive Windows stdout rewrap (e.g. `monte_carlo.py`) replace stdout with a block-buffered wrapper that `python -u` does not unbuffer (a manually-constructed wrapper, not the interpreter's own stream). Fix: every `trader queue submit` of a progress-printing python job needs `--env PYTHONIOENCODING=utf-8 --env PYTHONUTF8=1`. Also use plain ASCII in print statements — a stray `Δ` or other non-cp1252 char crashes with `UnicodeEncodeError` under Windows console encoding even with the env vars set. Evidence: `feedback_queue_stdout_buffering.md`; `research` skill LIVING GOTCHA #5.

**Queue-submitted python DRIVER scripts: two Windows launcher traps (2026-08-12)** — both hit wiring a `monte_carlo` driver for `tools/dsr.py`; both generic to any `trader queue submit -- py <script>`.
(a) *`py -3.11` in the argv dies instantly.* The launcher resolves `py` to concrete `python311.exe` and passes remaining args to THAT interpreter, so `-3.11` arrives as an interpreter option (`Unknown option: -3`, exit 2, ~5s, empty `run.log`, real reason only in `stderr.log`). Fix: submit bare `py <script>` — the version selector belongs in `%LOCALAPPDATA%\py.ini`, never in a queued argv.
(b) *A driver importing a multiprocessing module needs `if __name__ == '__main__':`.* Windows uses spawn, so every worker re-imports `__main__` (YOUR driver, not `monte_carlo`) — an unguarded top-level `main()` call re-runs the entire MC recursively. Surfaces as a `freeze_support()` traceback per worker in `stderr.log` while the parent's `run.log` keeps advancing normally, so the job looks healthy and silently burns cores. Fix: env setup stays at MODULE scope (workers must inherit it; `monte_carlo`'s knobs are module-level constants read at import time), only the `main()` call goes inside the guard. Check `stderr.log`, not just `run.log`, on any queued job that spawns a pool.

**peewee FK-per-row trap (silent 190k-roundtrip loop)** — Symptom: a bulk loop over Score (or any peewee model with a `DeferredForeignKey`) appears to hang at ~25% of one CPU core with nothing visible in `SHOW PROCESSLIST` (each roundtrip sub-millisecond, so no single query looks slow). Cause: accessing `.symbol` on a Score row fires one lazy SELECT per row via `get_rel_instance` — a 190k-row loop is 190k MySQL roundtrips. Fix: read `row.symbol_id` (the raw varchar FK column) in bulk loops instead of `.symbol`, or use `.tuples()`. Diagnose a suspiciously slow bulk loop with `Scripts/py-spy.exe dump --pid N` looking for `get_rel_instance` in the stack. Evidence: `feedback_peewee_fk_per_row_trap.md`.

**Scoring-lock cutoff drift blocks ALL score writes** — Symptom: `trader update`/`recalculate` fails with "Refusing score write" or a `ScoringVersionMismatch`-style error after touching `CALIBRATION_CUTOFF_DATE` or any other locked `SCORING` constant. Cause: the scoring-version guard fingerprints locked constants at capture time; changing one without re-capturing invalidates the fingerprint. Fix:
```python
from database.scoring_version_guard import capture_lock
capture_lock(AlgorithmVersion.get_or_create_current(), note="...")
```
then verify with `python tools/check_scoring_version_integrity.py`, and commit `algorithm_versions/scoring_locks.json` in the SAME commit as the constant change. Note: the CLI verb the error message references (`trader algorithm lock-scoring`) does NOT exist — the fix is the Python snippet above. Evidence: `feedback_scoring_lock_cutoff_drift.md`.

**`server.bat restart` hangs the agent foreground** — Symptom: running `server.bat restart trader-api` (or any verb) from an agent's foreground shell hangs indefinitely. Cause: a hidden persistent child process holds the shell's stdout pipe open. Fix: run via the PowerShell tool with `run_in_background: true`: `& C:\Development\server.bat restart -Service trader-api`. Do NOT use Bash `cmd.exe /c "server.bat ..."` — it prints the cmd banner and no-ops in ~0s with exit 0 while the OLD code stays loaded (a false-success trap, worse than a hang). Restart is required after editing `api.py`, `strategy_config.py`, `backtest_cascade.py`, `portfolio_param_manifest.py`, or anything `api.py` imports — the frontend (`:3000`) hot-reloads on its own, needs no restart. Verify with `GET http://127.0.0.1:5000/health` → 200. As of 2026-07, `server.bat` is NOT inside this repo — it lives at `C:\Development\server.bat` (parent directory), dispatching to `C:\Development\server.ps1`; both are outside `C:\Development\Trader`. Evidence: `feedback_server_restart.md`; cli.md DOC-VS-CODE MISMATCHES #4.

**Queue preemption can orphan a deep recalc's children** — Symptom: after the daemon preempts a task, untracked full-recalc python processes keep hammering MySQL even though `trader queue status` shows the slot free. Cause: the daemon's `kill_tree` (a psutil parent-chain walk) can miss a deep git-bash→bash→python cluster if an intermediate process died or reparented. Fixed: env-tag reaping (`TRADER_QUEUE_TASK_ID`/`TRADER_QUEUE_ATTEMPT` set on every child; `_sweep_tagged_orphans()` runs every ~90s tick; `force=True` at daemon startup). Manual reap if orphans persist: trace `ParentProcessId`; `trader queue hold <id>` FIRST (else the daemon just respawns it), then `taskkill /PID <top-live-bash-pid> /T /F`. Restarting the daemon itself: kill the daemon python process only (NOT its tree — children survive and the new daemon adopts them); `Stop-ScheduledTask` does NOT kill a detached daemon — need `Stop-Process <pid>` then `Start-ScheduledTask`. Evidence: `project_trader_close_queue_routing.md`.

**Editing engine/config files while a queued sweep is running hangs it silently** — Symptom: a queued sweep hangs for its full timeout with a near-empty log, no crash, no error. Cause: Windows multiprocessing re-imports modules FROM DISK at every per-window pool creation; editing `monte_carlo.py`/`strategy_config.py` mid-run kills a worker importing a half-edited file, and `pool.map` blocks forever waiting on a result that never arrives (classic Windows MP failure: initializer/import death looks like a hang). Fix: never touch engine/config files while a queued sweep that subprocess-imports them is in flight — docs/FINDINGS edits are safe, engine/config edits are not. Corollary: once a mechanism ships enabled in `strategy_config.py`, any new sweep's baseline arm must set `*_ENABLED=0` EXPLICITLY — a bare `{}` baseline silently inherits the shipped ON state. Evidence: `project_bdiv_onset_omens.md`; `research` skill LIVING GOTCHA #31.

**"Harness background runner IS NOT the queue"** — Symptom: `trader queue status` shows "0 cores used/N free" while a heavy job actually saturates them, and the daemon then admits a scheduled `trader update` ON TOP, colliding on tight-timeout MySQL. Cause: launching compute via the Bash/PowerShell `run_in_background: true` flag (or any raw detached process) bypasses the queue's CPU/DB admission accounting entirely — the queue only knows about resources it granted. Fix: **"I'm actively watching it this turn" does NOT exempt a job.** Any of `ScoreSimulator`/`recalculate`/`assess`/Monte Carlo/research-pack build/parquet-cache build is ALWAYS `trader queue submit`, even from a worktree, even read-only — a 10y `ScoreSimulator` capturing-simulate IS a full-universe MySQL bulk load, i.e. a sweep, not "iteration." If in doubt, queue it. Evidence: `feedback_use_task_queue.md`; CLAUDE.md "Long-Running Compute"; `queue-ops` skill.

**Mass score-row deletion: COPY-SWAP, never DELETE** — Symptom: a bulk `DELETE` on `scores` at a high deletion ratio crawls at ~1,500 rows/s (a full purge would take ~22h) or `DELETE ... LIMIT` mis-plans on MySQL 5.7 into a read-timeout zombie. Cause: the interleaved clustered PK `(symbol, date, version_id)` makes row-at-a-time deletion at scale pathological. Fix: copy survivors into a `CREATE TABLE LIKE` clone, parity-check row counts, atomic `RENAME`, drop the old tablespace (~2s), restore FKs with `FOREIGN_KEY_CHECKS=0` (instant INPLACE). Tool: `tools/purge_score_versions.py --below 69 --swap` (this exact invocation purged 152M→7.08M rows, ~120GB→~5.3GB, in ~36 min — as of 2026-07, `CADENCE_MIN_VERSION_ID=69` is the floor; never re-add a pre-v69 id). Evidence: `project_pre_v69_purge.md`.

**Sharded-ReSim budgeting + queue-timeout footguns** — Symptom: an 8-arm full-universe ReSim sweep gets killed ONE arm short of finishing. Cause: a full-universe `ScoreSimulator` arm costs ~18 min/shard (not the ~5 min a coarser prior note implied); an 8-arm run at 7 shards ≈2h20m blows a 2h queue timeout. Fix: budget timeout ≈ build-time + 20min×n_arms, and give the harness a skip-if-parquet-exists resume guard BEFORE the first launch (a resumed run then only re-does the missing shard-arms, ~1h instead of ~2h20m). Two sub-traps: (a) `trader queue wait N | tail` reports the PIPELINE's exit code (tail's 0) — a timeout can look like success; read the wait's own output text ("still running after timeout"), don't trust a piped exit code; (b) the queue KILLS at timeout (exit 15), so the parent's merge step never runs — merge shard parquets manually before analyzing. Evidence: `project_dampener_ablation_v72.md`; `research` skill LIVING GOTCHAS #23, #34.

**`_dump_trade_tape` polars schema-inference crash** — Symptom: a tape/parquet build over heterogeneous per-row dicts crashes with a dtype error deep into the run (e.g. past row 100). Cause: `pl.DataFrame(rows, schema=names, orient='row')` infers column dtypes from only the first ~100 rows; a column that's `None` early and a string later (e.g. a CT-tagged config's `ct` field only populated on some configs) crashes on the type mismatch. Fix: pass `infer_schema_length=None` on any tape/parquet build over heterogeneous rows. Evidence: `research` skill LIVING GOTCHA #7.

**`run_backtest` lives in TWO call sites — thread new features into both** — Symptom: a new per-signal feature (e.g. VIX) works in the main cascade backtest but the monthly `compute_and_store_temporal` vacuum call silently fails or no-ops, and `temporal-refresh` still exits 0. Cause: `compute_and_store_temporal`'s per-month vacuum call is a DIFFERENT scope than `run_cascade_backtest`'s main call — a feature var defined only in the main-call scope raises `NameError` there, which the vacuum call swallows. Fix: always read the surrounding `def` before threading a new `run_backtest` argument, and load/compute the feature in BOTH call sites (or drop the kwarg if the vacuum effect is genuinely negligible — single-month fresh starts rarely hit a DD gate). Evidence: `research` skill LIVING GOTCHA #9; see `ship-portfolio`/`research` Phase 6 13-consumer wiring list.

**No-default dataclass parity (`DteStrategyConfig`)** — Symptom: adding one new strategy field crashes on `STRATEGY_15DTE` instantiation even though you only meant it for 30-DTE. Cause: `DteStrategyConfig` fields have NO defaults, so every field must exist on BOTH `STRATEGY_30DTE` and `STRATEGY_15DTE` (the registry's `_check_schema` + every instantiation site require it). Fix: add the field to both configs; if genuinely 30-DTE-only, set the 15-DTE side to an inert/disabled value and register it as `not_wired` in `mechanism_registry.py` with a non-blank `reason`. Evidence: `research` skill LIVING GOTCHA #8; `deploy.md` 13-consumer checklist.

## 2. Evidence honesty

**Weekly features in a RECALC are look-ahead (root cause of the pre-v69 inflation)** — Symptom: a cohort mined on `WeeklyScore`-derived features (`w_mom`, `w_comp`, `w_bias`, `w_adj`, kijun, `wv_force1`, etc.) from RECALCULATED historical rows shows strong edge that evaporates when re-measured honestly. Cause: pre-v69, the weekly composite keyed on the CURRENT week (`_week_start(d) = d - timedelta(days=d.weekday())`) and `WeeklyScore` stores the COMPLETE Mon-Fri bar — so a recalc of a mid-week signal reads FUTURE bars relative to that signal date, while live `trader update` (point-in-time by construction) never had this leak. Decisive test: split the cohort's optTP by day-of-week — Monday≫Friday (Friday≈baseline) means look-ahead, not alpha (proof case: 70-74 `w_mom∈[5,8)` optTP15 went Mon 68.3→Fri 49.75). Fix: v69 (`8b59206c3`, 2026-05-31) fixed via point-in-time partial-week reconstruction + a transition blend — the "honest era" watershed; ~12pp of pre-v69 per-trade WR edge was this leak. The naive "last-completed-week" fix is ALSO wrong (too stale, demotes ~64% of 75+ signals). As of 2026-07, `CADENCE_MIN_VERSION_ID=69` means pre-v69 score rows are purged entirely — research old versions via research packs, never raw rows. Evidence: `reference_weekly_recalc_lookahead.md`; `find-and-ship-alpha` GUARD 3.

**Any stored COMPLETED-period aggregate used as a "partial" feature is look-ahead** — Symptom: a promising weekly/periodic feature nearly gets filed as a hard NULL because its z-score seems too good and vanishes on a sanity check. Cause: using a stored completed-period aggregate (any table storing exactly one row per finished period, e.g. `WeeklyScore`) as if it were a point-in-time partial reading injects post-signal bars. Fix: reconstruct the partial-period feature from raw bars (e.g. `PriceHistory` week-start through the signal date only, never the whole week), validate against production's actual partial states in `score_intraday_logs`. **When a closeout is about to file a hard "DO NOT RETRY" null, sanity-check the feature build for as-of correctness FIRST** — a look-ahead-confounded null is worse than no test (poisons future re-mining with false confidence). Evidence: `feedback_lookahead_feature_build.md`.

**PIT proxies are mandatory for any current-snapshot attribute applied to history** — Symptom: a mechanism keyed on market_cap/sector/shares-outstanding shows a strong historical gradient that partially evaporates on a stricter test. Cause: using the symbol's CURRENT snapshot attribute against historical dates is survivorship — only symbols that still exist (and often thrived) contribute their current attribute to old dates. Fix: `mcap_t = mcap_latest × close_t / latest_close`, anchored on the symbol's true latest close — apply this PIT proxy pattern to ANY current-attribute-on-history mechanism. Concrete instance: MCD's market-cap gradient looked like 8.2pp, collapsed to 2.6pp (still real, z=+2.61, much smaller) under PIT correction. Evidence: `project_v71_integrity_ship.md`.

**Mid-assess read is a race, not a result** — Symptom: reading assess/WR output while the process is still executing shows an inflated headline number that doesn't reproduce. Cause: the WR pass prints intermediate correlation/summary lines (e.g. "RTR Corr") WHILE the result row is still finalizing — reading at that instant captures a partial, unrepresentative sample. Fix: never read an assess result until its process EXITS. Two documented incidents both showed an inflated mid-write read (e.g. 61.6%/N5119/z+16.49 "SHIP") finalizing to a much smaller honest number (51.4%/N1338) once the process completed. Evidence: `project_honest_miss_sweep_keep_v70.md`.

**Cohort z-score is necessary but NOT sufficient for a portfolio ship** — Symptom: a mechanism with a strong per-trade cohort z (even z>+10) still nulls or reverses at the portfolio Monte Carlo level. Cause: correlated drawdown within the same cohort's trades can offset the per-trade alpha exactly — a signal winning more often per-trade can still lose the SAME sessions together, invisible at the per-trade level, showing up only in portfolio-level DD. Fix: stage every candidate — cohort profile → N=100 sweep (5-6 structurally distinct candidates) → N=300 gate on top 3-5 → N=500 ship gate on the winner. Don't skip stages because the cohort z looked strong; ≥3 documented cases show a strong cohort z reversing at N=300+. Evidence: `feedback_cohort_signal_validation.md`.

**MC noise floor at N=300 is large — N=500 for any ship claim** — Symptom: an N=150 or N=200-300 "winner" reverses when re-run at N=500. Cause: baseline-to-baseline seed variance at N=300 single-window is ~1.6-1.8× on compound and ±5-8pp on DD (branching in the bounded-fill breaker model is structural, not a bug). Fix: strict gates (Stage-3 T-gate, any final ship claim) need N=500+ per (window×arm); N=300 is screen-only; N=100 is probe-only. DD is more stable than compound as a metric — a 2-3pp candidate-vs-baseline DD delta consistent across ≥5 windows is real signal; a compound delta alone at N<300 is noise. Evidence: `feedback_mc_noise_floor.md`; `run-monte-carlo` skill.

**Full-faithful validation is mandatory for indicator-input changes — P0/sample approximations lie** — Symptom: a P0 prototype (10%-sample, or one mocking `_ph_cache={}`) predicts a WR lift, and the real recalc regresses instead (documented case: P0 predicted +4.51pp, honest production showed −13.1 to −14.1pp on 95+/85+/80+ tiers). Cause: mocking the price-history cache bypasses rare-event lift bands (breakout-push, divergence-push) that fire on <5% of signals but carry ±15pp of conviction — a P0 sample never sees them. Fix: `trader recalculate --force --full` (~25 min for 10y) + `trader assess --force` (~10 min) BEFORE claiming any WR lift from an indicator-input change; apply the ship gate to the recalc'd assessment output, not the P0 preview. Structural defense: ΔN>>15% on any primary tier between old and new assessment is a red flag even when headline WR looks good (the exact v42 −13pp lesson). Evidence: `feedback_indicator_validation.md`, `project_rolling_weekly.md`, `project_v40_svd_revert.md`.

**Small-screen/small-stock evidence does not generalize — always confirm full-universe** — Symptom: a 60-stock (or 64-name, or single-sector) screen shows a strong +6-7pp effect that reverses on the full universe. Cause: manual/curated screens are survivorship-biased by construction (tend to include only names someone already noticed winning) and have too little N for the effect's true CI. Fix: never ship on small-stock-screen evidence — documented pattern: a small screen shows +6.6pp, the full 771-2003-symbol universe shows a CI spanning 0 (or negative). Concrete instance: SuperTrend/PSAR trend-flip. Evidence: `project_supertrend_flip_null.md`; `deploy.md` hard warnings.

**A user's famous market anomaly can be index-specific and REVERSE on our own universe** — Symptom: a well-known stat (e.g. "SPY gains happen during market hours, not overnight") gets proposed as an entry-timing lever and appears to apply here. Cause: the stat was measured on an index (SPY); this codebase's 810-stock universe can have the OPPOSITE pattern (confirmed: our universe's overnight return dominates, intra−over is negative, reverse of the SPY stat). Fix: always confirm the premise on OUR OWN data/era first before spending compute chasing a famous anomaly — a plausible financial-media stat is not evidence about this specific universe. Evidence: `research` skill LIVING GOTCHA #24; `project_intraday_overnight_null.md`.

**Look-ahead resamples fake momentum/velocity signals — mine the point-in-time feature** — Symptom: a "VIX weekly-MACD" or similar rolling/weekly-resample momentum feature shows a huge cohort holding most of the drawdown-dollars, and turns out to be a tautology. Cause: a naive weekly resample (`dt.truncate("1w")` + `.last()`) maps an early-week signal date to that week's LATER close — pure look-ahead. Fix: for ANY "X's momentum/velocity/acceleration" idea, build the engine-faithful point-in-time version (recursive EMA using only past bars, or a strict last-COMPLETED-week resample) before mining it — a naive resample that looks like "73% of the drawdown dollars" will often evaporate or even INVERT once done honestly. Evidence: `research` skill LIVING GOTCHA #28; `project_vix_weekly_macd_null.md`.

**Honest full-fidelity A/B is achievable via sharded ReSim — don't settle for a proxy** — Practice (not a failure mode): a full-universe × 5y × N-arm honest mechanism A/B is cheap if built as `ScoreSimulator` per symbol-shard, all arms patched in-process via module-constant monkey-patches with try/finally restore (arms within a shard share one bulk load), joined to the `barrier_outcomes` DuckDB mirror by `(sym, date, overall)`, judged by delta-cohort WR (which signals the mechanism ADMITS/REMOVES vs the shared cohort) rather than bucket-table diffs. A validation arm that exactly replicates already-stored rows is MANDATORY before trusting any harness verdict (documented: 98.4% exact match proved the harness once, worth the extra arm every time). Evidence: `research` skill LIVING GOTCHA #30; template `experiments/integrity_audit_2026_06/ab_eval.py`.

## 3. Process & shipping

**Never env-gate production scoring or engine code** — Symptom: temptation to add `PHASE_X_ENABLED` or a "default OFF research knob" directly to a shipped scoring/engine module so a hypothesis can be tested in place. Rule: no `PHASE_X_ENABLED` env-gates, no flags, no "default OFF" research knobs in `database/utils/scoring.py`, `database/models/core.py`, `simulator.py`, `api.py`, `trader.py`. A failed hypothesis must leave ZERO trace in production code. Test instead via (1) `ScoreSimulator(scoring_fn=my_variant)` (kwarg at `simulator.py:163-166`, as of 2026-07) or (2) a runtime monkey-patch with `try/finally` teardown — patch BOTH `database.utils.scoring` AND every module that already imported the function BY NAME. Canonical template: `experiments/weekly_avwap/phase_i_wadj_blend_sweep.py`. (Distinct from Stage-3 portfolio mechanisms, which DO ship as `getattr(_cfg, 'X', default)` module-level reads — the shipped, wired form, not a research knob.) Evidence: `feedback_no_env_gates_in_scoring.md`; `process.md`; standards bar item.

**Version-bump order is now settled: bump the FILE, THEN recalc** — Symptom: new-formula scores get saved tagged with the OLD algorithm version ("v33 formula applied to v32 rows"), corrupting assessment and the dashboard. Cause: `Stock.calculate_scores_batched()` → `get_or_create_current()` reads the `ALGORITHM_VERSION` FILE, not git HEAD — if the file still points at the old commit while `recalculate` runs, every newly-computed row gets tagged wrong. Fix (proven sequence, v44/v46/v73/v74 ships): (1) commit scoring code, (2) `git rev-parse --short HEAD > ALGORITHM_VERSION` + commit (SEPARATE commit), (3) THEN `python trader.py recalculate --force --full`. Recovery if done wrong: bump the file, commit, re-run the recalc (costs the ~45-50 min already spent). **Known contradiction in auto-memory:** the `MEMORY.md` index one-liner states the opposite ("run recalculate --force BEFORE committing ALGORITHM_VERSION bump") — WRONG; the detailed memory file + `deploy.md`'s documented sequence + repeated ship precedent agree: file-bump, then commit, then recalc. Evidence: `feedback_version_bump_order.md`, `feedback_algorithm_version.md` (the two disagree on same-commit-vs-separate-commit granularity — deploy.md's separate-commit sequence is the newer/more-precedented, follow it); `deploy.md` section 4a.

**`trader assess`'s version resolution is a HEAD-pointer trap, not the active-scores pointer** — Symptom: on a dirty tree or mid-ship, `trader assess` (and tools built on `assess_scores.py`) silently assesses the WRONG version. Cause: verified against source (`assess_scores.py`, `get_or_create_version()` ~line 273-274, as of 2026-07) — it calls `AlgorithmVersion.get_or_create_current()` (the HEAD/pointer used for WRITING new scores), NOT `AlgorithmVersion.get_active_scores_version()` (the pointer the Flask API and dashboard actually READ). ## 4. Modeling & metrics

**DD is primary; compound above ~1e10% is theoretical, not a real claim** — Rule: rank every portfolio candidate by 5y WorstDD PRIMARY; treat compound as a non-regression sanity check only (within ±3 orders of magnitude of baseline — the exponent matters, the mantissa doesn't). MC compounds of 1e26-1e36% are unrealizable in practice (liquidity, broker caps, IV crush all bind long before that) — DD is the one metric that translates 1:1 to a real equity curve. Reject any "compound win at DD cost" framing — a >50% compound lift paired with >1pp of 5y DD worsening is the documented Phase-OP1 trap pattern, not a real win, unless the compound win crosses into the ~1e10%+ range where compound stops discriminating at all. Evidence: `feedback_dd_primary_compound_theoretical.md`; standards bar item 1; `ship-gates` Stage 3 T4/T7.

**collapse=0 on EVERY window including 2020-COVID is the non-negotiable floor** — Rule: for any held-book ship (Core, Sentinel, any non-opt-in profile), P(collapse) must be exactly 0% on every (window×mode) cell, NO exception for crash windows — a Phase-B screen run WITHOUT the `2020_crash` window has historically HIDDEN a collapse that only surfaced at Phase C/D, so always screen 2020_crash, every sweep phase, not just the final gate. **Execution cost is ASYMMETRIC — never model a flat round-trip spread** — Rule: `SLIP_ENTRY=0, SLIP_TP=0` (mid-entry and limit-TP fills are FREE — you're the liquidity provider); only FORCED exits (SL, hard-sell, dead-hold expiry) pay a half-spread, `SLIP_SL=SLIP_HARD=-0.015` (raise only this one knob to −0.02..−0.03 for a stress test). **Dead-hold is collapse-PREVENTING — HOLD ≫ CUT, don't build a cut/reallocation mechanism** — Symptom: an intuitive "cut the losing bag early and redeploy into a fresh high-score signal" idea (reallocation/displacement/CDR) keeps getting proposed and keeps nulling. A loser's slot also frees naturally in ~3 extra days on average — displacement buys almost no real turnover. Fix: before proposing ANY cut/hold/reallocation mechanism, mine the dead-hold OUTCOME distribution first (recovery vs expiry, by regime) — this has falsified 5+ separately-proposed variants (blunt realloc, regime-gated CDR, hard-sell-7, trailing stops, daily reposition). ## DrivePool wedge, milder variant: exactly-300s per-op = driver wait-state, and the uninstall path is a minefield (2026-07-23)
Second wedge flavor (after a USB reseat + reboot mid-arrival): every pool op — read, write, enumerate — completes after EXACTLY 300s (a 300,000ms CoveFS timeout expiring per operation, then answering). Members instant, zero disk/USB events, service startup clean. The exact-300s constant IS the diagnostic: driver wait-state, NOT load. "It's just Measuring" was tested and WRONG — the pool had measured for two days pre-reseat with zero stalls. Service restarts and plain reboots do NOT clear it. The uninstall→reinstall fix tier then hit three sequential landmines, each invisible until the previous one was cleared:
1. **PendingFileRenameOperations poisoned** (nonstandard `*N`-prefixed IObit leftovers + rolled-back-installer entries) — SURVIVES REBOOTS, boot processor can't parse it, installer refuses "system pending reboot" forever. Fix: `reg delete ... /v PendingFileRenameOperations /f` + delete the referenced junk files; do NOT loop rebooting.
2. **covefs service key zombied by uninstalling a wedged driver**: `DeleteFlag=1` + `Start=4`(disabled) + STOP_PENDING; reinstall over it "succeeds" but the service then dies with "CoveFS was not found". Fix: delete DeleteFlag, set `Start=1` (SYSTEM_START), reboot to load the fresh driver.
3. **ROOT\COVEFSDISK virtual SCSI bus device deleted by uninstall and NOT recreated** by reinstall or `/repair` (RC=3010): covefs runs but "Timed out waiting for all pools to finish mounting", `dpcmd list-pools` empty, refresh-all-poolparts and hint-poolpart are no-ops. Diagnostic chain: `sc query CoveFSDisk` = STOPPED 1077 + `reg query ...Enum /s /f CoveFsDisk /k` = 0 matches. Fix: devcon-install equivalent via SetupAPI (SetupDiCreateDeviceInfo with the CLASS name + DICD_GENERATE_ID — a hwid with a backslash throws 0xE0000205 — set hwid `Root\COVEFSDISK`, DIF_REGISTERDEVICE, then UpdateDriverForPlugAndPlayDevices with the oem INF). Device binds LIVE, no reboot; the pool remounted with its original volume GUID and drive letter (D:) intact — mount-manager identity survives the whole ordeal.
Meta-rule: after uninstalling a WEDGED kernel driver, audit all three surfaces (pending-renames, service-key DeleteFlag/Start, PnP device nodes) BEFORE trusting the reinstall; each failure mode masquerades as the next one down.

**2026-07-29 root cause + durable fix — it was the BOOT RACE all along.** covefs is a boot-start driver that mounts the pool ~10s after load (`WaitForVolumesOnMountMs`/`WaitForKnownPoolPartsOnMountMs`=10,000ms defaults) while the 15 USB enclosures enumerate over minutes (worst observed: stragglers ~12m50s after boot, amplified by USB devnode identity churn — 9 volumes re-installed as "new" devices on the 07-28 boot). A pool volume mounted mid-arrival enters the wait-state PERMANENTLY: every namespace op answers only after an exact per-op-class timeout (measured live: 30/90/120/300s — all multiples of 30s; volume metadata like `Get-Volume` stays instant). Nothing above the driver clears it — proven live 07-29: a service restart with all 25 parts registered within 30s plus a COMPLETED 4.5h measure changed nothing. Reinterpretation of 07-23: the uninstall→reinstall "cure" worked only because the recreated ROOT\COVEFSDISK device bound while all members were already online — mount-with-members-present is the actual cure; the reinstall was incidental.
FIX (shipped + reboot-validated 2026-07-29): set `CoveFs_WaitForVolumesOnMountMs` and `CoveFs_WaitForKnownPoolPartsOnMountMs` to 1,200,000 (20 min) via the Override field in `C:\ProgramData\StableBit DrivePool\Service\Settings.json` (the vendor surface — a bare registry edit gets overwritten by the service's config push) AND mirrored into `covefs\Parameters`. The driver now holds the D: mount until all known parts arrive; the 20-min ceiling is hit only if a disk is truly dead (then it mounts degraded, which DrivePool flags normally). Validation boot: D: mounted at boot+2m34s, count=25, zero missing-part warnings, dir 0.3s, write+delete 0.9s.
Secondary traps found en route: (1) `pnputil /restart-device` on the CoveFSDisk bus (ROOT\SCSIADAPTER\0000) is the no-reboot un-wedge lever in principle, but query-remove gets vetoed by processes parked on D: I/O (accumulate from boot-time tasks; kill doesn't release them until their blocked I/O returns) → once the fix is staged, the reboot IS the recovery. ## `price_history.close` is SPLIT+DIVIDEND ADJUSTED; option strikes are AS-TRADED (2026-07-25)

## A cohort flag defined over a REALIZED holding window is outcome-conditioned (2026-07-25)

Flagging a trade by "did event X fall inside its holding window" using the REALIZED exit date conditions on the outcome, because exit date IS an outcome: TP winners exit in ~4 days, dead bags run to the ~15-day expiry. A longer window is mechanically more likely to contain the event AND mechanically more likely to be a loser.

Measured (`experiments/event_noise_decomp/FINDINGS_T4_exante_earnings.md`, v74 tape, N=853k): the ex-post flag gave earnings-spanning positions EV −0.3419 vs +0.0375 base (gap −0.3794), WR 26.7% vs 70.7%, dd_conc 2.40 — a textbook Pareto-lever signature, entirely fake. Redefining the flag ex-ante (entry + NOMINAL 20-calendar-day hold) gives +0.0118: a 97% collapse and a sign flip. The honest cohort actually holds *shorter* (4.44d vs 5.79d) because an event tends to RESOLVE a position early — which is why the ex-post filter selects against it.

**Diagnostic tell:** an effect ~10x anything else in the system (−0.38 against a +0.0375 base) that collapses when the window is redefined from realized exit to nominal hold. **Rule:** define every event-window flag from the ENTRY date plus the NOMINAL hold, and report the hold-duration composition of both cohorts as standing proof the confound was addressed.

## `REPLACE INTO` nulls every column absent from the payload — a new column dies on the next upsert (2026-07-29)
`PriceHistory.bulk_build` used `insert_many(...).on_conflict_replace()`. In MySQL that's `REPLACE INTO`, which is DELETE+INSERT, not an update: any column not in the payload resets to its default. The table had exactly the columns bulk_build wrote, so this was invisible for years.

The moment `close_unadj` (as-traded price) was added, it became a silent data-destroyer: `trader update` writes today's bar through bulk_build every run, so each run would have WIPED the as-traded price for every date it touched — no error, no log line, just NULLs appearing in a column nobody was watching. Changed to `on_conflict(preserve=[...])`, which updates only the supplied columns; behaviour is identical for pre-existing callers.

Second trap inside the fix: putting the new column in `preserve` re-creates the bug in a subtler form — a multi-day pull carries `close_unadj=None` for its older rows, and `preserve` would faithfully write those NULLs over good history. The column must be written on INSERT and left untouched on conflict.

**Generalizable:** before adding a column to a table, grep every writer for `on_conflict_replace`/`REPLACE INTO`. A partial-payload upsert is a column-eraser. Assume any column you add is invisible to existing writers and will be nulled by them.

## A one-to-one reverse map silently DUPLICATES a company when two symbols claim one vendor ticker (2026-07-29)

(2) If the global install vanishes (node reinstall, wiped `%APPDATA%\npm`), the MCP fails LOUDLY — the tripwire, by design — while run.cjs silently falls back to `npx gitnexus@latest`; re-pin before running any analyze. (3) Editing `NPX_REF` in run.cjs is futile — analyze rewrites that file on every run; the global binary is the only durable pin.

## A dead ticker keeps growing plausible rows: flat-close + volume=0 tail = delisting/rename signature (2026-08-22)
